# 07 · 技术笔记：并发与 RAG 踩坑

> 这些是本次压测和代码审查得到的实战结论。换框架/平台后仍适用，因为问题本质是**资源模型**，不是某个库。

## 1. 基线数据先行

- 56,426 块，假模型 2.3 秒/答。
- 10 并发 p95 42 秒；100 并发 p95 315 秒。
- 100 并发：97% TTFT ≥ 120 秒，29 次重排排队超时，32 次 90 秒假超时。
- 结论：延迟随并发近似线性增长，瓶颈是串行化资源。

## 2. 同步 SSE 会占满线程池

- FastAPI 里 `def` 端点跑在 anyio 线程池，默认上限 **40**。
- 同步生成器（StreamingResponse）在等待上游 token 时，每次 `next()` 都占一个线程。
- 40 路流式问答后，登录、列表、健康检查一起排队。
- 现象：CPU 不高，但 `/api/health` 延迟 2 秒甚至超时。
- 解法：
  - `async def` + `httpx.AsyncClient.stream`，SSE 纯异步；
  - 检索/推理放独立 `CapacityLimiter` 或进程池；
  - 健康检查做成轻量异步端点。

## 3. GIL 是隐形杀手

- BM25 查询对 5.6 万块做纯 Python 循环，全程持 GIL。
- 40 个线程同时跑检索，事件循环和其他线程都拿不到 GIL。
- 表现：
  - 读 LLM 流的线程被饿死，`time.time() - t0 > 90` 触发假超时；
  - 日志出现“流式生成超过 90s”，但假模型只需 2.3 秒。
- 解法：
  - 倒排索引（只给命中词打分）或外部检索引擎；
  - 检索移到独立进程/进程池；
  - 避免在请求线程里做大循环。

## 4. 重排信号量是硬瓶颈

- `RERANK_CONCURRENCY = 2`，排队最长 120 秒，超时静默降级。
- 每次对 20~45 个候选、每条最多 512 token 做 CPU 推理。
- 并发 10 时约 15 秒排队；并发 100 时约 150 秒，直接雪崩。
- 解法：
  - 候选降到 10~16；
  - ONNX `intra_op_num_threads=2`，避免每个会话抢满核；
  - 并发按核数配置；GPU 加速；
  - 高负载按规则跳过重排；
  - 独立重排服务 + 批量。

## 5. 上游 LLM 的并发额度

- 公司网关每把 Key 约 2 路并发（代码注释实测）。
- 一次提问可能 1~3 次调用（改写、拆解、主回答、续写、配图核对）。
- 实测 100 问产生 125 次上游调用。
- 解法：
  - LLM 网关统一限流/排队/Key 池；
  - 减少不必要调用（无历史不改写、无需拆解不拆）；
  - 每用户 Key 作为兜底；
  - 429 时给出明确等待时间，不要无限重试。

## 6. 没有连接池

- `httpx.post` / `httpx.stream` 顶层调用每次新建连接。
- 并发高时握手/TLS/端口开销大，网关侧连接数暴涨。
- 解法：共享 `httpx.Client/AsyncClient`，配置 `limits` 和 keep-alive。

## 7. 冷启动与缓存

- 启动预热只建 BM25；首个向量查询会 `np.load` 115MB、全量解析 5.6 万行。
- 多个线程同时首次查询会重复加载，内存翻倍、GIL 卡死。
- 解法：
  - 启动时预热 BM25 + 行缓存 + 向量（mmap）+ tokenizer + 模型；
  - 加锁保证只加载一次；
  - 未就绪返回 503/进度，不让请求触发同步构建；
  - 向量用 `mmap_mode="r"` 共享页缓存。

## 8. 状态在进程内存/文件

- BM25、行缓存、向量缓存、答案缓存、答辩 session 都在进程内。
- 多 worker 会内存 ×N、缓存/会话不一致；`registry.json`/`users.json` 写入无跨进程锁。
- 解法：
  - 检索进程池 + 只读索引；
  - Redis 放缓存/会话/限流；
  - Postgres 放用户/注册表/日志；
  - 不要直接 `--workers N`。

## 9. Nginx/网关的 SSE 坑

- 默认 `proxy_buffering on` 会把 token 攒到最后一次性返回。
- 需要：
  - `proxy_buffering off; proxy_cache off; gzip off;`
  - `proxy_read_timeout 300s;`
  - `proxy_http_version 1.1; proxy_set_header Connection "";`
  - 上传 `client_max_body_size 100m;`
- 浏览器代理 PAC 也要把内网域名设为直连。

## 10. Linux 迁移的具体坑

| 问题 | 现状 | 处理 |
|---|---|---|
| EMF/WMF 转图 | 用 PowerShell + System.Drawing | Linux 需 LibreOffice/ImageMagick，或接受缺失 |
| .doc 抽取 | antiword（可选） | Linux `apt install antiword` |
| 中文字体 | 依赖系统字体 | 安装 Noto CJK |
| 路径 | registry 存 Windows 绝对路径 | 迁移时重映射或重新索引 |
| 服务托管 | .bat/隐藏进程 | systemd |
| 文件锁 | 进程内锁 | 多进程用文件锁/数据库 |

## 11. 安全与配置

- `config.json` 明文存 API Key/管理员口令；仓库里还有旧隧道私钥。
- 生产用环境变量/密钥文件；权限 600；轮换默认口令。
- 不在日志里记录完整问题/答案中的敏感信息。
- 对外材料脱敏。

## 12. 上线前自检

```
[ ] 检索不在 Web 进程里跑大循环

[ ] 上游有网关限流/Key 池

[ ] 监控能看到每阶段延迟和队列

[ ] 备份和回滚演练
[ ] 100 并发压测通过或有明确 429 策略
```

## 13. 一句话总结

**并发问题不是“换个框架”能解决的，而是把 CPU 密集、长连接、共享状态从 Web 进程里拿出去。** 谁拥有资源、谁排队、谁限流，想清楚这三件事，换不换 LangChain 都不重要。

## 14. 修复效果复盘（2026-11）

把上面的结论落到本项目后的实测结果（脱敏）：

| 问题 | 改动 | 实测结果 |
|---|---|---|
| BM25 全量循环持 GIL | 内存 CSR 倒排，只扫命中词 | 75–172ms → 1.6–7.0ms（20–49x），top-k 逐位不变 |
| 多线程重复加载 115MB 向量 | 按查询 mmap + meta 缓存 + 写者优先锁 | 首载 104.6ms/8×115MB → 8.5ms/共享页；加载 28.8ms → 1.2ms |
| 重排并发 2 排队雪崩 | 并发 1；保留完整候选与重排，不静默降级 | 吞吐 0.28 → 0.30–0.32 job/s；单请求 7.2s → 3.9s |
| 过载时用户干等 127s | 三层准入 + 立即 429 | 50 并发首字 127.4s → 8.5s |
| 健康检查排在线程池后 | `/api/health` async | 空闲 8–11ms（基线 1985ms） |
| 同步 SSE 占线程池 | `chat_async` / `stream_async` + 异步生成器 | 50 并发首字 127.4s → 15.2s；30/50 持平 |
| 建索引内存峰值未知 | 建索引采样 + 持久化状态 | 56,870 块峰值 192.5MB / 213s |
| 图片知识进不了检索 | 摘要 + OCR 独立 chunk | 答案可直接引用图中文件用途 |

**取舍**：重排仍是唯一成本中心，吞吐在 4 并发饱和（约 0.20 条/秒）。
`global_max` 不是越大越好：8 只增延迟不增吞吐，最终取 6。要提高并发，
必须先提高重排吞吐（GPU / 更小模型 / 独立服务），而不是继续加队列。

## 15. 后续工程化（2026-11）

### 15.1 索引任务与多用户数据一致性

- 索引从前台线程改为**持久化队列**：`queued/running/done/failed/interrupted`
  状态落盘，失败重试，服务重启后可恢复；前端按状态显示真实进度。
- 不同知识库默认 **2 个索引 worker 并行**，同一个库仍串行；
  大库索引完成不代表向量已补齐，健康检查单独暴露向量一致性。
- `registry.json` 的读-改-写加锁并原子写；上传、索引状态、chunks 临时文件
  都使用唯一临时名。并发建库/改名/索引完成不会互相覆盖，同名文件并发上传不互踩。
- 索引内存采样是进程级全局，多个 worker 同时开 `tracemalloc` 会串台，
  因此只在单 worker 时采样。

### 15.2 日志与可观测性

- Docker `json-file` 适合看即时控制台，但容器重建后会丢；生产额外把
  stdout/stderr 按天写入挂载卷，保留 30 天。
- 日志里保留 `[coach]`/检索/模型耗时和 `stop_reason`，失败时记录
  `parse_failed ... raw=...`，排障不再靠猜“是检索慢还是模型慢”。
- 健康检查、预热、索引任务、问答统计分开，不把文件 I/O 和重活塞进 `/api/health`。

### 15.3 把等待变成可解释的状态

- 大模型阶段无法给出真实百分比，但可以按“检索 → 组织问题 → 模型思考”分阶段显示，
  同时显示已等待秒数和动态进度条。
- 能提前算的就提前算：PPT 上传后预生成首题；每题答完后台生成诊断；
  最终汇总只补缺失题 + 总体评价。实测单题诊断约 10–13 秒，
  3 题汇总约 15 秒（本机 4 核、无图 PPT；原实现一次性生成 10 题约 1–2 分钟）。
- **不要预生成依赖未来信息的内容**：下一题追问依赖候选人刚回答什么，
  强行预生成只会问错方向；只预生成确定能确定的部分。
- 后台任务要有并发上限：诊断 worker、参考答案预生成都限制并发，
  避免后台任务抢走前台出题/问答的模型额度。

### 15.4 引用与文件定位

- 正文角标和引用区用稳定的 `data-ref` 编号一一对应；点击角标展开引用区、
  滚动并高亮对应条目，而不是让用户自己数第几条。
- 文件预览页左侧带目录树（源目录/上传、按真实目录分组），当前文件高亮；
  点击引用文件名打开预览时携带命中文本，在正文里分段匹配并定位高亮。
- 表格片段含 `|`、长片段跨段时，不能直接整段 `indexOf`；按单元格/句号切短片段
  再匹配，命中率明显提高。

### 15.5 按知识库隔离会话

- 问答上下文、消息列表、滚动位置按知识库保存；来回切换时恢复各自的记录，
  不再把 A 库的问题带到 B 库。
- 上下文开关仍是全局偏好；关闭后不发送历史，但界面仍保留各库的可见记录。
- 会话只存在当前页面内存，刷新后清空；要跨刷新保留需要外置会话存储（Redis/DB）。
