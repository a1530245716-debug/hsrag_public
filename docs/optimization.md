# 并发重构实录：从排队 315 秒到可控的 429

> 脱敏版实施记录（2026-11）。基线、环境与复现方法见 `case-study.md`、
> `technical-notes.md`、`evaluation.md`；本文只讲**改了什么、实测多少、为什么这样取舍**。
> 所有客户名、账号、内网地址与真实文档均已移除。

## 0. 一页结论

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 50 并发首字 p50（全部放行） | 127.4s | **15.2s**（阶段 2 异步化后） |
| 50 并发首字 p50（每用户限 2） | 127.4s | **8.5s**（其余立即 429） |
| `/api/health` 空闲 p95 | 1985ms（100 并发时） | **8–11ms** |
| BM25 单次查询（56k 块） | 75–172ms | **1.6–7.0ms** |
| 过载行为 | 用户干等 2–5 分钟 | **立即 429 + `Retry-After`** |
| 评测 | 5/6 | **6/6** |

**没有宣称 100 并发都能被服务。** 实测吞吐在 4 并发就饱和（约 0.20 条/秒），
继续放行只是让所有人排队；最终用准入控制把 `global_max` 定在 6，超出明确 429。

## 1. 根因（有代码行与压测证据）

1. **同步 SSE 占满线程池**：`def` 端点 + 同步生成器，40 路流式问答后，登录、列表、
   健康检查一起排队；100 并发时 `/api/health` P95 到 1985ms。
2. **BM25 全量循环持 GIL**：对 5.6 万块做纯 Python 循环，40 个线程同时检索时，
   事件循环和其他线程拿不到 GIL；日志出现「流式生成超过 90s」，而假模型只需 2.3s。
3. **重排信号量只有 2 路**：每次 20–45 个候选做 CPU 推理，100 并发排队约 150 秒。
4. **没有连接池**：`httpx.post`/`httpx.stream` 每次新建 TCP/TLS。
5. **网关额度**：每把 Key 约 2 路并发，30 并发即触发 429。

## 2. 阶段 1：先止血，不要让人干等

- 三层准入：全局活跃问答数、每用户并发数、每 IP 每分钟次数；
- 超限**立即** `429 + Retry-After`，不排队；
- `/api/health` 改 `async def`，从线程池挪出；
- 名额回收：整数计数 + 锁 + 后台回收，避免信号量泄漏后只能重启。

**实测（50 并发，每用户 2）**：首字 p50 从 127.4s 降到 8.5s；被拒请求立即 429。
健康检查空闲 8–11ms。

## 3. 阶段 2：把长连接从线程池拿出去

- `chat_async` / `stream_async` + 共享 `httpx.AsyncClient`（按事件循环缓存，
  `limits` 控制连接池）；
- SSE 改成异步生成器，客户端断开时停止上游请求；
- **同步实现完整保留**，出问题改一行即可回滚。

**实测（mock LLM 2.3s/答，全部放行）**：

| 并发 | 阶段 1（同步 SSE） | 阶段 2（异步 SSE） |
|---|---|---|
| 10 首字 p50 | 35.9s | **13.6s** |
| 30 首字 p50 | 61.3s | **15.2s** |
| 50 首字 p50 | 64.9s | **15.2s** |
| 50 首字 p95 | 96.6s | **15.2s** |

30 并发和 50 并发的首字几乎相同，说明**线程池不再是瓶颈**。没到 <10s，
因为下一个瓶颈是重排。

## 4. 检索侧：倒排、mmap、重排

### 4.1 BM25 倒排索引

- 在 `BM25.build()` 里从已有词频表构建内存 CSR 倒排：词 → posting 切片；
- 只给命中词的块打分，不再对全部 5.6 万块做纯 Python 循环；
- 5.6 万块：136,422 词 / 300 万 posting / 24MB；构建 +1.3s；
- 查询 75–172ms → **1.6–7.0ms**（20–49 倍），12 条查询 top-20 **逐位相同**；
- 建完释放原词频表，约省 330MB。

### 4.2 向量按需 mmap

- `np.load(..., mmap_mode="r")` 替代全量加载：28.8ms → 1.2ms；
- 8 线程同时首载不再重复 8×115MB，页缓存共享；
- **Windows 坑**：被 mmap 的文件无法 `os.replace`（WinError 5）。长期持有会让
  向量重建失败。最终改为「每查询打开 → matmul → 关闭」+ 每库写者优先读写锁 +
  替换重试，收益保留、重建不回归。

### 4.3 重排调参：不要用「静默降级」换指标

- 16 vCPU 实测：默认线程 + 并发 1 是 0.30–0.32 job/s；并发 2 只有 0.28 且单请求
  耗时翻倍；`intra_op_num_threads=2` 更差；
- batch 4/8/12/16/24 实测差异很小；本机没有 GPU provider；
- 曾经把排队超时降到 10s，结果排队超过 10s 的请求**悄悄失去重排**、答案质量
  不可见地下降。已撤回：超时保留 120s，过载由准入控制 429 决定，
  被放行的请求保留完整候选与完整重排。

### 4.4 图片知识文本化

- 图片摘要与 OCR 不再只留在图片索引里，而是按文档写成 sidecar，索引时拆成
  **独立 chunk**（摘要一行、OCR 一行）；OCR 行明确标注「可直接引用」，
  避免模型把它当「图片说明」忽略；
- 两个库共约 2,900 张图（1,640 + 1,225）完成摘要，1,125 张有 OCR；
- 实测提问「SJSMXn、SJSJG、SJSFX、SJSGB 分别是做什么的」，
  答案直接引用图中 OCR 的业务明细，而不是答「没找到」。

## 5. 阶段 3：检索内核解耦

- 窄接口 `RetrievalBackend.retrieve(kb_id, query, top_k) -> list[Chunk]`；
- `LocalBM25Backend` 包一层现有实现，逻辑不变；`MockBackend` 用于验证 feature flag；
  `RagflowBackend` 目前是骨架（未注册，避免误选）；
- 4 处检索调用改走 `backend.retrieve`；
- **Chunk 契约**：`id/path/text/score` 必需；`rerank_score` 等可选；
  `doc_id/title/chunk_index/metadata/raw_score` 预留给 RAGFlow；
- 配置按 mtime 热加载，可按库切换后端，不用重启。

## 6. 多用户压测：单账号测不到全局层

单账号受 `per_user_max=2` 限制，先撞每用户限制，永远看不到 `global_max` 的真实效果。
改用 **16 个测试账号 + 多 token 轮转**，每档 20 个并发请求，mock LLM 2.3s，
真实 BM25 + 重排（56k 块）：

**容量曲线（global = 并发数，全部放行）**

| 并发=global | 首字 p50 | 首字 p95 | 墙钟 | 放行吞吐 |
|---|---|---|---|---|
| 4 | 9.2s | 15.9s | 20.0s | 0.201/s |
| 6 | 15.1s | 25.6s | 29.5s | 0.203/s |
| 8 | 22.9s | 36.7s | 41.8s | 0.192/s |
| 12 | 30.3s | 52.7s | 58.8s | 0.204/s |
| 20 | 50.1s | 85.8s | 94.5s | 0.212/s |

**固定 global、20 并发（看 429）**

| global | 放行 | 429 | 首字 p95 | health p95 |
|---|---|---|---|---|
| 4 | 4/20 | 16 (80%) | 16.1s | 652ms |
| 6 | 6/20 | 14 (70%) | 25.9s | 562ms |
| 8 | 8/20 | 12 (60%) | 37.6s | 497ms |
| 12 | 12/20 | 8 (40%) | 53.8s | 530ms |
| 20 | 20/20 | 0 | 85.8s | 319ms |

**结论**：放行吞吐从 4 并发起恒定在 **0.20 条/秒**；加 `global_max` 不提高吞吐，
只让首字延迟线性变长。最终取 **6**：p95 压在 26s 内、队列有界，超出明确 429。
如果产品能接受 37s p95，8 也可以，但它不增加吞吐，只减少 429。

**口径**：测试机同时跑生产实例与开发实例，绝对延迟偏悲观；mock LLM 只模拟 2.3s，
真实网关更慢。曲线形状和拐点可信。

## 7. 验收

- `eval` 6/6（6 条真实风格问答；此前基线 5/6）；
- `/api/health` 空闲 8–11ms，过载时 0.3–0.65s；
- 建索引（56,870 块）峰值 192.5MB / 213s（tracemalloc 口径，Python 分配下界）；
- 索引任务持久化状态、失败重试 2 次、重启标记 interrupted；
- 向量完整性校验：`chunks.jsonl` 行数与 `vectors.npy` 行数不一致时禁用向量、
  降级纯 BM25，并在 health 里暴露。

## 8. 下一步

1. **提高重排吞吐**是提高并发的唯一有效杠杆：GPU、更小模型、批量、独立重排服务。
   batch/线程已试到顶，换模型需要 eval + 压测 A/B，不能只看速度。
2. **状态外置**（Redis/Postgres）后才能多 worker、滚动发布；当前单进程重启会清零
   限流计数与会话。
3. **部署到服务器**：Nginx SSE、数据迁移、监控、备份、回滚演练。
4. **图片展示**：答案底部统一「相关截图」区并显示 caption，而不是按段落猜位置；
   避免「图文不符」，同时保留图片里的知识。
